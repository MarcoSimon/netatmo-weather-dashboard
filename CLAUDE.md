# Netatmo Weather Dashboard

A wall-mounted dashboard for a Netatmo weather station: an old Android tablet hangs on the wall and permanently shows the state of the house and the weather. Everything runs inside the house — poller, database, HTTP server and display are all on the LAN. There is no cloud component, no TLS and no access from outside; the Netatmo app covers that case.

**The design lives in `docs/design.md`.** It is the source of truth for goal, architecture, decisions and assumptions — read it before starting anything, and update it when a decision changes rather than only recording the change in a commit message. An installation may keep its own facts (the building, the devices, its measurements) in a gitignored `CLAUDE.local.md`.

- `npm run poll` — the poller. Every cycle: refresh the token when due, record modules and status from `getstationsdata`, bring every module's series up to date from `getmeasure`, log, sleep. **A failed `getstationsdata` does not cost the values:** the cycle backfills the module list of the last good cycle and skips only that cycle's status; only the first cycle after a start has no list and ends. **The first start imports the whole history** through the same backfill, spread over ordinary cycles — for four years of three modules that was about 1,080 pages, 26 cycles and **five hours** of poller runtime, not the three the page count suggests, because Netatmo's 503s cost whole cycles. Ctrl-C (or `kill -INT`) stops it promptly: the wait between cycles and the pause between pages are abortable, so only an HTTP call already in flight is waited out. A `kill -9`, a crash or a power cut skips the cleanup and leaves `token.json.lock` behind; the next start takes it over when the pid it names is gone and says so in a warning. A lock whose pid is running is still refused — also when that pid now belongs to an unrelated process after a reboot, which fails safe and needs the lock deleted by hand.
- `npm run serve` — the HTTP server on port 8080: `GET /api/modules` (every module with its newest point, its newest status from `getstationsdata` and the server's `now_utc`), `GET /api/modules/<id>/series?hours=<n>` (default 24, at most 168) with the room's `co2_baseline` (the 2nd percentile of the preceding week, for the window guess), `GET /api/forecast` (the Open-Meteo forecast, `src/openMeteo.js`), `GET /api/settings` (the install-time settings from `.env`) and the static files in `public/`. **The forecast is the server's only outbound call:** fetched hourly for `FORECAST_LAT`/`FORECAST_LON`, held in memory and never in the database, kept through a failed fetch (retried after ten minutes) and dropped after six hours; without coordinates the server runs without it. **A separate process from the poller, and read-only on the database** (`src/reader.js`): it needs no Netatmo credentials, never touches `token.json`, and refuses to start before the poller has created the schema instead of creating it itself. Measured against a real database while the poller wrote: a week of one module (about 2,000 points, 191 KB) in 21 ms, including the filter for faulty points. **Series leave out faulty values** — out of bounds, or a spike against the median of its neighbours — and the newest point leaves out values out of bounds.
- **The wall page** is `public/index.html` with `app.css`, `app.js`, `format.js`, `chart.js`, `pressure.js`, `humidity.js`, `airing.js`, `window.js`, `night.js`, `status.js`, `forecast.js`, `evening.js` and `power.js`: plain ES modules, no build step. Each tile's curve is one `<svg>` with five `<path>`s (time marks, key-value lines, line, low and high dot) created once; a refresh only replaces their `d` attributes, and a series is fetched again only when its module has a new point. A tap on humidity, CO₂ or pressure swaps the curve for 30 seconds (under a room's humidity curve with the other rooms' air in this room's terms, in a line every tile keeps free), a tap on the curve itself shows its last seven days for the same 30 seconds, fetched only while it shows, a tap on a room's airing label shows its reason in the curve's place — every value inside against outside and one sentence, scrolling with a fade at the edge with more beyond it when it does not fit — and while no rule applies the label is a quiet "Lüften?" that answers what airing would do, a tap on the outdoor tile's morning night low brings back the 24-hour low and high, and a tap on its "Vorhersage" label shows the forecast there (one delegated listener and at most one timer per tile). **The page renders in three modes**, switched by `body[data-mode]` from `evening.js`: day, evening from sunset − 15 minutes, and night from 22:00 to 06:00 — black, no tile backgrounds, and every tile down to its name, temperature and airing label until a tap wakes it for 30 seconds through the same timer as the curve swap. The times are defaults that `.env` overrides per install. **A woken tile keeps the night's black background** and the night's lettering: a lighter rectangle in a dark room is a lit rectangle. **The backlight is the other half and belongs to the kiosk browser**: a tablet's IPS panel glows through a black page, and its own minimum can be too bright for a dark room, so the screen goes off rather than dim. Fully Kiosk Browser (PLUS) switches it off at night and on in the morning; the page adds only what a schedule cannot — `keepDark()` in `app.js` calls `fully.turnScreenOff()` half a minute after the last touch at night, because a wall woken at 02:00 would otherwise burn until morning. **The split is deliberate: the page never owns switching the screen *on*.** A hung page that leaves the wall dark all day is a worse failure than one that leaves it bright all night. `window.fully` is absent in every other browser and the call is guarded, so nothing of this happens on a desk. `http://<host>:8080/?mode=day|evening|night` pins one, which is the only way to look at the night rendering on the wall in daylight, and the way out of a wall too dark to read — **a pinned mode never sleeps**, or the one tool for checking the night would switch itself off while being looked at; `?diag` overlays the CSS viewport, `devicePixelRatio`, browser version, mode and time zone the device reports. Headless Chrome (`--headless=new --screenshot --window-size=1280,800`) gives a desk preview; it does not exit on its own because the page keeps a timer running, so kill it once the PNG exists. **Kill a DevTools-protocol instance by its pid, and check that none is left:** `--remote-debugging-port=9222` is taken by the *first* browser still running, so a later run silently drives the older, stale page while `fetch('/app.js')` from that same page returns the new file. `pgrep -f remote-debugging-port=9222` settles it. A desk preview is not the wall check. **Leak check:** drive headless Chrome over the DevTools protocol with the page's `setTimeout` delays divided by 60 and a writer adding a point per module every second (dropping the oldest, so series keep their size); read `Runtime.getHeapUsage` and `Performance.getMetrics` after `HeapProfiler.collectGarbage` once per simulated hour. Measured over about 1,400 ticks with every series refetched each tick, and again with a random tap every 0.3–1 s on top: the heap levelled at 834–840 KB (941–948 KB with taps) from the fourth simulated hour on, with 109 (145) DOM nodes and 3 listeners throughout. **Repeated for the week behind a tap on the curve**, on Chrome 156 and the demo station, with half the taps on a curve, the week fetched and dropped about 2,100 times over 24 simulated hours, and the page before it run alongside as the baseline on the same machine: 1,312–1,359 KB against 1,291–1,329 KB from the eighth simulated hour on, about 1,327 against 1,298 KB at rest afterwards, 230–248 DOM nodes and 8 listeners in both runs — the added code, no growth. The absolute figures differ from the first measurement for both runs alike, so **compare against a baseline run, not against the numbers here**. **Again for the key-value lines**, against the commit before them as the baseline: about 30 KB more, at rest (1,386–1,409 against 1,321–1,377 KB) and with every week showing (about 1,785 against 1,754 KB). **The heap has two levels while taps run:** about 1.35 MB at rest and about 1.8 MB while a tile holds its week, so a single reading lands on either; compare rest readings, and the top of the upper level, across runs. A single reading taken mid-refresh can be a third higher, twice as high once, and back at baseline a minute later; read the trend, not one sample.
- `npm run demo` — the dashboard on invented data at `http://localhost:8090` (`DEMO_PORT`): a temporary database seeded from `src/demoData.js` with a week of three modules, an invented forecast through the real parser, and the default settings, so it needs no account, no `.env` and no network. The values end at the start, so the tiles go stale after 35 minutes. **The README's screenshots come from it**, rendered with headless Chrome and Roboto as in the desk preview below, taps by clicking each tile's `[data-key]` or `.airing`; render them again when the page changes visibly.
- `npm run windows -- <YYYY-MM-DD> [<YYYY-MM-DD>]` — what the window guess saw, per day and room, judged like the wall page does. Read-only; compare it with openings noted down while they happened.
- `npm run charge:deploy` — puts the charge loop on the Shelly plug (`shelly/charge.js`, `docs/tablet-setup.md` §4): the plug's fail-safe (`initial_state: on`, `auto_on` after 4.5 h), the kiosk browser's URL in its key-value store, the script uploaded, started and enabled at boot. Safe to run again. **The script only switches off**, at 75 %; switching on is the plug's own timer. `npm run -s charge:log >> charge.log 2>&1` is the record from outside: level, plugged, socket and power once a minute, and a warning when the socket is on and the tablet does not charge. Both read `SHELLY_*` and `FULLY_*` from `.env` — **quote a value with `#`**, which Node's `--env-file` otherwise cuts as a comment.
- `npm run poll:once` — a single cycle. Use this while setting up; it exercises the whole path including a token rotation.
- `node --env-file-if-exists=.env src/poll.js --cycles=<n>` — a bounded run. With a wide `TOKEN_SKEW_MS` every cycle is forced to refresh, which puts a day's worth of rotations through the chain in minutes instead of waiting for real expiry.

The npm scripts read `.env` through `node --env-file-if-exists`, so **there is no dotenv dependency** — and a missing `.env` produces our own message instead of a Node stack trace. All npm scripts pass `--disable-warning=ExperimentalWarning`, because `node:sqlite` still announces itself as experimental on every start. `POLL_INTERVAL_MS` shortens the interval for a test run; the 10-minute default is the floor that matters in production. `TOKEN_SKEW_MS` widens the renewal window and is only meant for that stress test.

**Measured against a real station over two unattended days:** 146 cycles, **15 rotations, none rejected**, no manual intervention. The access token is valid for **180 minutes**. **The refresh token does not expire with it** — renewals that ran two hours late because the host was asleep were accepted, and so was one about 82 hours past the access token's expiry. A restart after an outage of days therefore needs no re-authentication; 82 hours is the longest gap tested, not a known limit.

**`getstationsdata` returns HTTP 503 roughly 7 % of the time** (10 of 146 calls), never more than twice in a row. Retrying in the next cycle is enough — do not add a backoff. Such a cycle still fetches the values through `getmeasure`, which can answer 503 as well, so a visible age on the dashboard is still needed: a tile frozen for twenty minutes is normal here. **`getmeasure` can fail for longer than `getstationsdata`:** once it answered 503 in three cycles in a row, and a room's newest point was 49 minutes old before the next cycle closed the gap unattended. That is past the 35-minute staleness mark, so the tile rightly went stale; still no backoff.

**A superseded refresh token was once still accepted 38 minutes after being replaced.** This was learned by accident — a bug (since fixed) sent the old token after a mid-cycle failure, and Netatmo honoured it. Do not build on this: it is one observation of a grace period whose length and existence are undocumented, and the next attempt may be rejected.

**The project has no runtime dependencies and should keep it that way** as long as the standard library covers it — `fetch`, `node:test` and `node:sqlite` are all built in. `node:sqlite` needs **Node 22.13 or newer**, which is why `engines` says so.

## The guiding principle

**The display answers questions, it does not show sensors.** This is the whole reason the project exists next to the Netatmo web UI, and it is the criterion any UI change is measured against: every tile must trace back to a question actually asked in the household ("should I air the room", "is it colder outside than inside", "how was the night", "is a window still open", "is a module about to go flat"). A tile that only renders a measured value has to justify itself.

## Architecture

    Internet                  |  House (LAN, no TLS)
    --------------------------+--------------------------------------------
    Netatmo Cloud  --10 min--> poller (Node) --writes--> SQLite
                   <-backfill-           <-> token.json (rotating refresh token)
    Open-Meteo     --forecast-> HTTP server (Node) --reads--> SQLite
                                        --JSON + frontend--> tablet(s)

Five facts carry this design:

- **The refresh token rotates.** Every renewal invalidates the previous token, so the token file is live credential state, not configuration. There must be **exactly one writer**, and it must replace the file atomically (write a temp file, then `rename`). **The file, not a variable, is the source of truth:** every cycle re-reads it, and a rotated pair is persisted the moment it arrives, before anything else in the cycle can fail. An earlier version held the token in memory and only committed it once the whole cycle had succeeded — a 503 from `getstationsdata` right after a refresh then discarded the rotated pair and sent the superseded one next time. Losing or racing on that file stops the display and forces a *manual* recovery at the Netatmo portal — the single worst failure mode this project has.
- **The first token pair comes from the portal's token generator, not from an OAuth flow we implement.** Each installation registers its own app at dev.netatmo.com with scope `read_station`, and **with no redirect URI on purpose**: the portal refuses to generate a token while one is configured, and the two are mutually exclusive. Do not add one "for completeness" — it disables the generator and buys a login flow that would be written, tested and then never run again, for an app that serves exactly one account. Renewal afterwards is the ordinary `refresh_token` call and needs the client ID and secret from `.env`.
- **The backfill makes 24/7 unnecessary, and it is the only source of series.** Netatmo keeps the full history at five-minute resolution and serves it through `getmeasure`. Each module continues after its newest stored point, so after any outage the next cycle starts exactly where the last one stopped. The stored series is always a gapless prefix of Netatmo's. `getstationsdata` is **not** a source of values: its `dashboard_data` is identical to the newest `getmeasure` point, and polling it every ten minutes sees only every other point. It supplies the module list and the per-cycle status (battery, radio, Wi-Fi, firmware), which `getmeasure` cannot deliver after the fact.
- **Ten minutes is the floor.** The station measures every five minutes but uploads only about every ten, two points at a time. Polling more often buys nothing and only brings the rate limits into view (50 requests per 10 s and 500 per hour per user, per Netatmo's documentation). The first import is the one time they matter, which is why it is capped at 50 pages per cycle, one second apart.
- **SQLite is one file**, via `node:sqlite`, and backup is a file copy. One wide `samples` row per `getmeasure` point, keyed by module and `time_utc`, with one nullable column per quantity. New modules add rows, never columns. The schema is versioned through `PRAGMA user_version`. **Measured: 38 bytes per point, 3.8 MB per module and year.**

## Domain notes

- **Airing is decided on absolute humidity, never relative.** 90 % at 5 °C outside is *drier* air than 55 % at 21 °C inside. Both absolute humidity and dew point follow from the Magnus formula over temperature and relative humidity, so no additional sensor is involved — but a comparison of the two relative values gives the opposite, wrong answer. This is the one calculation the project stands on; it belongs in a pure, unit-tested module.
- **CO₂ only exists in indoor modules.** The airing recommendation is therefore per *room* — each indoor module against the outdoor module — not per house.
- **Thick masonry walls lag the outside by hours.** In an old house with stone walls, a room's air settles toward its walls, not only toward the outside, so a room can cool on its own after warm air came in. The window guess has to allow for it; `docs/design.md` has the cases.
- **Modules come and go.** A station has a base unit, an outdoor module and up to three additional indoor modules, plus rain and wind sensors. The layout grows from three to six modules, so treat modules as a list and never wire up fixed tiles. Rain and wind are not further tiles but their own presentations (rain totals, wind rose).

## The display device

**The setup is in `docs/tablet-setup.md`** — account, kiosk browser, brightness, charging and the recovery tests, step by step, so a factory reset or a replacement device costs an evening rather than a round of research. Keep it current; an installation's own device details belong in `CLAUDE.local.md`.

**The target is an old Android tablet: Android 10, Chrome or WebView ≥ 139, 1280×800 CSS pixels at `devicePixelRatio` 1.5, in landscape, in Fully Kiosk Browser.** Chrome has required Android 10 since Chrome 139 (August 2025), so on such a device the engine freezes at the next raise; plain HTTP on the LAN and a page without build step keep that harmless, so do not reach for the newest platform features. After any long break, check the engine with `?diag` rather than assume it — **Chrome and the kiosk browser's WebView update separately.** Three constraints follow:

- **3 GB of RAM on an old device, and a page that stays open for weeks.** Keep the frontend lean and leak-free; the standing insurance is an hourly self-reload of the page.
- **Permanent charging swells the battery.** Use the firmware's charge limit where it holds, and otherwise cycle the charger through a switchable socket driven by the battery level the kiosk browser reports — a Shelly plug whose own script switches it *off*, while its auto-on timer is the only thing that switches it back *on* (`docs/design.md`, *Charging socket*; the measured drain is in `docs/tablet-setup.md` §4: plan with the daytime figure, 5–7 %/h).
- **Night matters.** A bright dashboard in a dark living room at 23:00 is unusable, so the dimmed, reduced evening rendering is a feature, not a polish item.

**Old iPads are ruled out.** iOS 9 does not trust the Let's Encrypt ISRG Root X1 certificate and cannot open modern HTTPS sites at all, and Safari 9 would additionally need an ES5 build.

## Project language: English

**Everything that lands in the repository or on GitHub is in English** — issues and ticket comments, commit messages (subject and body), PR titles, descriptions and review comments, branch names (`feat/poller-backfill`), documentation, and code including identifiers, comments and test descriptions.

## Workflow

- **Feature branch required:** substantial changes, refactorings and review-driven rework (more than 2–3 files or unclear scope) go on a separate branch (`git checkout -b feat/<topic>`), never directly on `main`.
- **Pull requests** reference their issue with `Closes #N` / `Fixes #N` on their own line.
- **Commit messages:** Conventional Commits, e.g. `feat: …`, `fix: …`, `docs: …`.
- **CI runs `npm test` on every pull request against `main`** (`.github/workflows/ci.yml`). It listens on `pull_request` only, so a direct push to `main` gets no CI signal.
- **Verify before claiming done:** run the checks yourself and read the actual output — no success claim without evidence. For a bugfix, cross-check by reverting the fix and confirming the new test actually fails without it.
- **Verify on the wall, not only on the desk:** a UI change is only done once it has been looked at on the tablet at its real distance. A laptop screen at 60 cm lies about legibility.
- **Documentation sync (Definition of Done):** immediately before every PR, check the documentation for two things — whether the change needs to be *added*, and whether it makes an *existing* statement inaccurate. Sweep `README.md`, this file and `docs/`, not only the sections you edited. Due updates belong in the same PR.

## Conventions

- **Secrets never land in the repository.** `.env`, `token.json`, the SQLite file and `CLAUDE.local.md` are gitignored and stay that way; `.env.example` documents the shape. The token file in particular is a live, rotating credential — treat a leaked one as burned and re-authenticate.
- **Split pure logic from IO.** Meteorological maths (absolute humidity, dew point, trends, night min/max) and the Netatmo response parsing are pure functions with unit tests. HTTP calls, the token dance and file writes sit in thin modules around them and are verified by running the thing, not by mocking it.
- **Timestamps are UTC in storage, local time in the UI.** Netatmo returns `time_utc`; keep it that way in SQLite and convert at the edge. Night min/max and daily aggregates are local-time concepts and are the place this will bite — pin `TZ=Europe/Berlin` in any test that touches them.
- **Store everything, display little.** The poller writes every value it gets, at full resolution, forever — faulty points included. What the dashboard shows is a separate decision and currently spans hours to days, and **faulty points are dropped when the server reads** (`src/plausible.js`), never when the poller writes: a dropped value becomes null, a gap in the curve, and is never replaced by an estimate.
