# Wall dashboard — design

The source of truth for what the dashboard is for, how it is built and why.
When a decision changes, change it here, not only in a commit message.

## Goal

An old Android tablet hangs on the wall and permanently shows the state of the
house and the weather. It is read from two metres away, in passing, without
anyone touching it. A house may have more than one such wall; they all get the
same page.

**Success criterion:** the display is what gets checked in the morning instead
of the Netatmo app — and the decision whether to air the rooms is made from it.

## Guiding principle

The display does not show sensors, it answers questions. That is the whole
difference to the Netatmo web UI and the only reason to build this. Every tile
must trace back to a question actually asked in the household:

| Question | Derived from |
| --- | --- |
| Should I air the room? | CO₂ + absolute humidity inside vs. outside |
| Is it colder outside than inside? | the difference, not two numbers |
| How was the night? | the night's low on the outdoor tile |
| Do I need a jacket? | outdoor module + forecast |
| Is a window still open? | CO₂ and temperature following the outside |
| Is something wrong with the station? | battery, radio, last contact |

### Why airing is the centrepiece

The question cannot be answered from relative humidity — which is why nobody
answers it from the Netatmo app. 90 % at 5 °C outside is *drier* air than 55 %
at 21 °C inside. Going by relative humidity means under-airing all winter.

Absolute humidity (or dew point) gets it right, and both follow from the Magnus
formula over temperature and relative humidity — values the station already
delivers. Worked example:

- Living room 21.0 °C / 55 % rH → 10.1 g/m³, dew point 11.6 °C
- Outside     5.0 °C / 90 % rH →  6.1 g/m³, dew point  3.5 °C

A difference of 4.0 g/m³: airing removes moisture. Read as relative humidity
(90 % against 55 %) the same situation would look like "do not open a window".

## Architecture

    Internet                  |  House (LAN, no TLS)
    --------------------------+--------------------------------------------
    Netatmo Cloud  --10 min--> poller (Node) --writes--> SQLite
                   <-backfill-           <-> token.json (rotating refresh token)
    Open-Meteo     --forecast-> HTTP server (Node) --reads--> SQLite
                                        --JSON + frontend--> tablet(s)

The backfill path is the load-bearing one: Netatmo keeps the history itself and
serves it through `getmeasure`, so the poller catches up on whatever it missed
after every restart. The host therefore does **not** have to run around the
clock — a laptop can do it during setup, and a small always-on machine such as
a Raspberry Pi once the wall is up.

## Decisions

| Question | Decision | Rationale |
| --- | --- | --- |
| Display device | an old Android tablet: Android 10 or later, Chrome/WebView ≥ 139, 1280×800 CSS pixels at `devicePixelRatio` 1.5, in Fully Kiosk Browser | A 10" tablet at 1920×1200 reports exactly this viewport, and the layout is measured against it. Chrome updates through the Play Store, so the engine can be current — but only while Chrome still supports the device's Android, and on an old tablet that has been in a cupboard it is often years behind, so check with `?diag` rather than assume. LCD, so no burn-in. **Old iPads are ruled out:** iOS 9 does not trust the Let's Encrypt root and cannot open modern HTTPS sites at all. |
| Operation | local, on a host on the LAN | Access is only needed on the LAN. That removes TLS, the cloud database, free-tier limits and storing secrets with third parties. Moving to another host is a file copy plus a unit file per process. |
| Language | Node | The task is fetching HTTP and writing JSON; no ecosystem advantage on another side. |
| JavaScript or TypeScript | plain JavaScript, server and page alike | **The wall page has no build step**, so it keeps working once an old tablet's engine is frozen — browsers do not run TypeScript, so it would need a compiler and a build artefact in `public/`, and the file served would no longer be the file in the repository. **The project has no dependencies**, and TypeScript would be the first, even as a devDependency. Node could run `.ts` on the server without a build, but that would split the project into two languages. The mistakes that would hurt (the Magnus formula, the airing rules, the parsers) are pure functions under unit tests, which catch more there than types would. **Revisit when** a misspelt field actually slips through: the step then is JSDoc types checked by `tsc --checkJs --noEmit` in CI, which adds a devDependency but no build step. |
| Storage | SQLite, one file, `node:sqlite` | Backup is a file copy. `node:sqlite` is built into Node 22.13 and later, so there is no dependency and nothing to build. Measured: 38 bytes per point, **3.8 MB per module and year**. |
| Source of the series | `getmeasure` only | The station measures every five minutes, and the newest `getmeasure` point is identical to `dashboard_data`. A ten-minute poll of `getstationsdata` would store every other point, through a second write path. `getstationsdata` still supplies the module list and the status (battery, radio, Wi-Fi), which exist nowhere else. |
| Table layout | one wide row per point | `samples` is keyed by module and `time_utc`, with one nullable column per quantity. The quantities are fixed by the hardware, new modules add rows rather than columns, and temperature and humidity of the same instant stay in one row for the airing calculation. |
| Getting the first token | portal token generator, no redirect URI | The portal refuses to generate a token while a redirect URI is configured — the two are mutually exclusive. Each installation registers its own app for its own account; a full authorization code flow would be a login flow that gets written, tested and then never run again. |
| Poller and server | two processes; the server reads only | A crashing or misbehaving server must never be able to take the token file with it, so it runs apart from the poller, needs no Netatmo credentials and opens the database read-only. It refuses to start before the poller has created the schema rather than creating it — that would make it a second writer. WAL mode lets both run at once; the server sees each page the moment the poller commits it. The price is a second unit file. |
| Tiles | temperature large; humidity and CO₂ small; the air pressure small on the outdoor tile, with its tendency arrow; the age on every tile | Noise is stored but not shown: it answers no question. Only the base unit measures pressure, but it is the same air indoors and out and belongs with the weather, so it sits on the outdoor tile — sea-level pressure in whole hPa, uncoloured, and left out while the base unit's own reading is stale, so the outdoor tile's age never vouches for it. Rain and wind modules get no tile. Dark background, since the screen hangs in a living room. |
| Airing recommendation | per room against the outdoor module: a label beside the room's name — "Lüften", "Kurz lüften", "Nicht lüften" — and its reason for 30 seconds in the curve's place after a tap; while no rule applies, a quiet "Lüften?" that answers on demand | **Rules, first match wins:** (1) CO₂ ≥ 1,000 ppm → air, briefly if (2) or (3) would also apply; (2) room ≥ 60 % and the outside air ≥ 1 g/m³ more humid → do not air — the humidity trap beats cooling, mould outweighs comfort; (3) room ≥ 24 °C and warmer outside → do not air; (4) room ≥ 24 °C and ≥ 3 °C cooler outside → air, it cools; (5) room ≥ 60 % and the outside air ≥ 1 g/m³ drier → air, it dries; otherwise nothing. The humidity rules compare **absolute** humidity (Magnus, Sonntag 1990 constants, over water; `public/humidity.js`). "Too dry" is no rule: in four years of history the rooms were below 40 % for under 1 % of the time. Every condition has an enter and a leave threshold (CO₂ 1,000/900, humidity 60/58 %, warm 24/23.5 °C, water 1/0.5 g/m³, cooler 3/2 °C, warmer 0.5/0 °C), evaluated over the day's series, so the page keeps no state and a label survives a single sensor step. Room points are paired with the nearest outdoor point within 10 minutes; a recommendation resting on a stale pair is not shown. Everything is computed in the browser from the series the tiles fetch anyway (`public/airing.js`). **Simulated over four years** (every 10 minutes, 24-hour windows, faulty points dropped): silent 64–70 % of the time; the label changes one to four times a day. **Display:** "Lüften" and "Kurz lüften" stand in an amber box with dark text, the loudest thing on the page, so red stays with the measured values; "Nicht lüften" is the answer "nothing to do" and keeps plain muted text, because a box on every label makes none of them catch the eye. The label says what to do, the reason says why — a table of every value the rules look at and one sentence. **A reason that does not fit scrolls** instead of being cut: with the server or power line at the foot of the page the tiles lose height, and a sentence cut mid-line was seen on the wall. Android shows its scrollbar only while scrolling, so the text fades out at whichever edge has more beyond it — two lines at the foot, one at the top, where a deeper fade swallowed the table's head; scrolling counts as reading and restarts the 30 seconds. **Asking on demand:** the rooms are silent most of the time, and exactly then there was nothing to tap when someone asked "should I air now?". So while no rule applies, the label's slot carries "Lüften?" in a grey box — a question, not a recommendation, so it does not break "one that is always on is noise". Its answer starts with "Kein Grund zu lüften." and says what airing would do, humidity first and then temperature, by the rules' own margins and hysteresis: "Die Außenluft hätte drinnen nur 45 % – Lüften trocknet den Raum.", "… macht den Raum feuchter", or "… ändert die Feuchte kaum"; for temperature "kühler" from 3 °C and "wärmer" from 0.5 °C. Within the margins it says what airing *changes* ("kaum"), not that the two sides are equal. Three sentences at most. **The table is the same for every reason:** whoever asks gets the whole picture, not only the values of the rule that fired. A column per side, a row per value — CO₂ (inside only), °C and % — and **the units name the rows**, because a column of labels made the table too wide for a 1280 × 800 tile. **The outside air in the room's terms:** a g/m³ row is the right comparison but not a readable one, so the outside's humidity carries what it would be at the room's temperature behind an arrow: "90 → 32 %". That is the trap in the scale the tile already uses. It goes through the vapour pressure, not the grams — warmed air expands — so 90 % at 5 °C is 32 % at 21 °C, not the 33 % a g/m³ ratio gives (`humidityAt`). Above 100 % the air would condense, on the walls, and the value reads "≥ 100". Showing only the derived value was rejected: a "Draußen" column saying 32 % while the outdoor tile says 90 % contradicts the tile. Since the arrow is not obvious at first sight, **every humidity sentence names the number behind it** ("Die Außenluft hätte drinnen nur 32 %"). At night "Lüften?" is left out: the first tap wakes the tile instead. |
| Window open | a guess per room — "Fenster auf?" in the airing label's slot, in a grey box, and since when and why behind a tap | Built from real openings rather than from the textbook "falling indoor temperature": with the outside only 2.5 °C colder the temperature barely moves while CO₂ falls clearly. **Two signals, each a 20-minute least-squares fit** (a single 5-minute step at a small excess turns sensor noise into an apparent opening): the **air change rate** from the decay of the CO₂ excess over the room's baseline — ≥ 3 per hour is an opening, a closed room stays well below 1 — and the **cooling rate relative to the inside–outside difference** — ≥ 0.4 per hour, which a closed room exceeds in fewer than 1 % of the history (p99 0.20–0.30; open rooms reached 0.4–0.8). CO₂ is judged only with ≥ 100 ppm of excess, temperature only with ≥ 1.5 °C of difference. **"Still open"** cannot come from CO₂ once the excess is gone, so it comes from temperature: an open room follows the outside, a closed one decouples. The guess ends when the room warms against the outside, when its cooling stays below 0.15 per hour for 15 minutes, or after three hours without anything to go on — **but the temperature closes only an opening it saw** (a cooling rate of at least 0.25 per hour at some point). **Latency follows the draught, not the size of the opening:** with a draught through the house the guess came 5–10 minutes after opening and went 15–16 minutes after closing; a single room fully open without a draught peaked at 3.8 air changes an hour and came and went about 20 minutes late. A 15-minute fit would halve both but invents openings that never happened. **The CO₂ baseline** is the 2nd percentile of the room's preceding week, delivered with the series (`co2_baseline`): Netatmo calibrates itself, rooms read 370–520 at their lowest depending on the week, and a baseline from the page's single day would sit too high on a day without airing. **Display:** the guess takes precedence over an airing recommendation — while a window is open, "Lüften" is moot. Its box is grey, not amber: it reports, it does not ask for anything. How long is in the reason, not the label, which would otherwise push the room's name out of the tile. The question mark says it is a guess, and the reason says the label lingers after closing — without a number, because on the wall it went 15 to 32 minutes after closing. **Known limit: a short airing is found only after it ends** — the 20-minute fit needs the fall inside its window. **Accepted:** the guess infers an opening from its consequences and cannot be exact about when; **a question too many beats one too few** — a label lingering on a closed window costs nothing, a window forgotten on a winter day chills the room. Exact answers belong to contact sensors on the windows. **Old masonry walls** ("The house" below) mislead the temperature signal when the outside is warmer than the rooms: the walls hold the air still while CO₂ shows several air changes an hour, and after the windows are shut a room cools on its own toward its walls. **So the temperature closes only an opening it saw, and an opening only CO₂ saw ends when CO₂ builds up again** — rising ≥ 150 ppm per hour over the fit *and* standing ≥ 75 ppm above the baseline — or after three hours. **Late was chosen over early:** a lingering "Fenster auf?" sends someone to check, while a window reported shut too early is the one that gets forgotten. The two CO₂ thresholds are set against false closings: a ten-minute bump from cooking next door and a sensor wandering 30–70 ppm above the baseline with the window still open. Over four years this changes the end of about a quarter of the openings, most of them later (median +30 minutes). **Still open:** a room whose temperature *did* see a warm inflow is still closed by the quiet rule once it relaxes to its walls; a fix has to keep the case where the room followed the outside and the quiet rule was right. `npm run windows` lists what the rule saw per day, for comparing with openings noted down while they happened. **A value the newest point lacks is a dash in the reason**, as on the tile, and never an older value: a point without CO₂ during an opening found by CO₂ once made the reason throw, and the wall froze with the room's tile moved to the front. |
| Rooms compared | under a room's humidity curve, for the 30 seconds it shows after a tap: every other room's air at this room's temperature, "Arbeitszimmer-Luft hier: 49 %", one line per room, above the low and high | The question "50 % at 21.6 °C here, 52 % at 20.6 °C there — is one room drier?" cannot be answered from the tiles. **Measured over three years of two rooms** (286,519 pairs): they hold the same air 91 % of the time by the airing rules' 1 g/m³, and the tiles' relative values mislead about a quarter of the time — 7.9 % they point the wrong way, another 15.8 % they differ by 3 % or more for the same air. The answer is "the same" nine times out of ten, which rules out anything always on and puts it behind the humidity tap. **In the scale of the tile:** the other room's air brought to this room's temperature (`humidityAt`), read against the tile's own humidity with no arithmetic — 49 % next to 50 % is the same air. "≥ 100" where it would condense; a room whose newest point is stale or lacks a value is left out (`otherRooms`). **The low and high stay**, so **every tile reserves one line under its curve**, empty at rest; a curve that shrank whenever the line filled would jump on each tap. A third room brings a second line, and that curve shrinks by a line while it shows. |
| Faulty points | dropped when the server reads, never when the poller writes: out of bounds, or a spike against its neighbours; a dropped value becomes a gap | A real history holds spikes of one to three points — a base unit that fell over reported CO₂ above 4,000 ppm — and a seven-hour plateau at 782 hPa; any of them in the last 24 hours dictates a curve's scale and the day's low or high. *Store everything* stays: the database keeps every point, and the filter is reversible. **No smoothing:** a rolling median would flatten the real values — the 0.1 °C staircase, fast CO₂ changes, the low and high — and still miss the plateau, which is its own median. Instead two rules only drop points. **Bounds** per quantity (temperature −40 to 65 °C, humidity 0–100 %, CO₂ below the sensor's 5,000 ppm ceiling, sea-level pressure 940–1,060 hPa) apply to every point, the newest included. **A symmetric Hampel test** drops a point further than 5 scaled MADs, and at least 1.5 °C, 8 %, 400 ppm or 2 hPa, from the median of its neighbours within ±30 minutes — with as many points on each side, because the station sometimes adds points a minute apart, and a lopsided neighbourhood turned a real drop of CO₂ during airing into a false spike. It needs three neighbours on each side, so the newest points are judged about 15 minutes later, and the reader reads half an hour beyond a window to judge its edges. Rain and wind are not tested; they are spiky by nature. A candle next to a module is dropped too — on purpose, the wall shows the room. **Known limit:** the tail of a jump that decays slowly is not caught. The pressure tendency keeps its own 15 hPa guard. |
| Stale after | 35 minutes | A point reaches the database up to twenty minutes after it was measured, and a 503 costs one more ten-minute cycle. Beyond that, the tile dims its values and flags its age. The age runs on the server's clock, so a wrong date on the tablet cannot make every tile look stale. One or two lost cycles stay below the mark, three do not — which happens, and is what the mark is for. |
| Tile order | outdoor first (left), then the base unit, then the indoor rooms | "How is it outside" is the most frequent question and the reference every room is compared against, so it gets the first glance. It holds as modules are added — top left in a 2×2 grid, first in the upper row of six. Within a type the module id decides, so the order needs no setting. |
| Humidity colour | indoor humidity coloured by comfort: red ≤ 30 %, orange 35, yellow 40, green 45–55, teal 60, blue ≥ 65 %, continuous in between; only the number | After the order of a comparable sensor app: every hue appears once, so a colour never stands for two humidities. It answers "is this room too dry or too damp" from across the room. Outdoor humidity stays uncoloured — 90 % outside is ordinary weather. It is a comfort reading of *relative* humidity and does not replace the airing recommendation, which compares absolute humidity. |
| CO₂ colour | green ≤ 800 ppm, yellow 1,000, orange 1,200, red ≥ 1,400, continuous in between; only the number | "Good", "still acceptable", "air the room". The stops follow EN 16798's indoor air categories (about 400, 600 and 1,000 ppm above outdoor air of ≈ 420 ppm) and the Umweltbundesamt, for which 1,000 ppm is the limit of hygienically harmless air. Its "unacceptable" 2,000 ppm comes far too late for a prompt to open the window, so red is reached at 1,400. |
| Poll interval | 10 minutes | The station measures every five minutes but uploads only about every ten, two points at a time. Polling faster buys nothing. |
| Visible history | the last 24 hours inside each tile: temperature at rest, any other value for 30 seconds after a tap on it; a tap on the curve shows the same quantity's last seven days for 30 seconds | Everything is stored, but the display shows the day — the last 24 hours rather than "today", marked at local midnight and noon. At rest, only temperature gets a curve; a curve for every value is the Netatmo web UI again. **Tap to swap:** a tap on humidity, CO₂ or pressure replaces the tile's curve with that value's last 24 hours; a tap on the value again, or on the temperature, returns at once, and after 30 seconds the tile returns by itself. The resting state stays untouched — a passer-by never finds the wall in a statistics view — while each curve still answers a question: did airing help, since when is the air stale, is the weather changing. The tapped value is underlined, and the low/high line carries its unit once, after the high. Its low and high are neutral, not blue and red: on the humidity scale red is the dry, low end. Minimum spans are 10 %, 200 ppm and 5 hPa. **A missing value keeps its tap target:** Netatmo sometimes delivers a point without one of the module's quantities, following the module's radio link rather than its sensor. A quantity the module's type measures but whose newest point lacks it is a muted "– ppm" that opens its curve like the number would, and the curve shows the gap. Nothing is estimated and no older value is carried over. Each tile carries its own curve, scale and 24-hour low and high, so it grows to six modules without a layout change and needs no legend. A gap of more than 15 minutes breaks the line, and a curve never spans less than 2 °C, so an indoor room's 0.1 °C steps stay flat. The curve is read from two metres as a shape; the marks and the low and high are for a closer look. The low and high read "Min: 23,8 °C – Max: 24,8 °C", the low in blue and the high in red; a dot in the same colour marks each on the curve, so the curve says *when* and the line below says *how cold*. An indoor room holds its low or high for hours, so the dot sits at the *last* point at that value. The line is not smoothed. **A week behind a tap on the curve**: "how has the outside temperature developed over the last few days" is a question the day cannot answer. The tap swaps the window, not the quantity, so it works on any curve showing — humidity, then the curve, is the week's humidity — through the same timer, and a second tap returns at once. The axis is a dashed line at each local midnight and the weekday under each day's noon; fourteen "0 Uhr / 12 Uhr" labels do not fit a tile. A day whose noon sits within 4 % of an edge stays unnamed, so depending on the hour today has no name — **decided from a render**, as was leaving out a "7 Tage" marker: the number of midnight lines says it. The low and high then cover the week, and the outdoor tile's night low does not apply. The week, about 2,000 points per module, is fetched from `?hours=168` only while a tile shows it and dropped once every tile is back at rest, so the resting wall's memory does not grow; it is drawn unsampled, which at 1,000 units of width is about two points per unit. Longer ranges, which need downsampling and a presentation of their own, are left for later. **Key values as horizontal lines**: 0 °C on the outdoor temperature ("did it freeze?"), and on a room's curves the airing rules' own thresholds, 60 % humidity and 1,000 ppm CO₂ — so the curve says since when a room has been past the point its label reacts to, and whether airing brought it back. **Only once reached** in the window shown (0 °C or below, 60 % or 1,000 ppm or above): the wall was meant to stay calm, and a line on every curve all the time would be decoration; a line that appears is the message. The scale is never widened to bring a threshold into view, except for a reached one the whole curve lies beyond — a day below zero throughout gets its line at the top edge. **Solid**, in the grey of the dashed time marks, so a value reads apart from a time where the two cross, as the week's midnights cross the frost line; its value stands small at the left end above it, the oldest and least read stretch of the curve, since a tile has no axis that would name the line otherwise. Both decided from a render. Outdoor humidity gets no 60 % line: outside air sits above it most of the time, and the threshold is a room's. **Left out:** a line at the room's CO₂ baseline — it moves with Netatmo's self-calibration (370–520 ppm between weeks) and would pretend to be a fixed value, and the curve's low already shows how far an airing got. |
| Night low | outdoor tile only, from 05:00 until 09:00, and at least an hour after the low — so until 10:00 at the latest: the line below the curve reads "Nacht: 11,6 °C (6:40)", the lowest temperature from 18:00 the evening before until 09:00 (or now), with its local time; a tap brings back the 24-hour low and high for 30 seconds | The 24-hour low does not answer "how cold was it last night": the outdoor low comes around sunrise, and at 07:00 the 24-hour window still reaches back to yesterday's sunrise — read at 07:00 over 1,434 days, it was off the night's low by ≥ 1 °C on 32 % of days and by ≥ 3.3 °C on one in ten. The night from 18:00 to 09:00 holds the low of a noon-to-noon day on 92 % of days. **Outdoors only:** in a room, "how was the night" is a question for a bedroom module. The blue dot marks the night's low while the line shows it, and the red one is left out, so curve and line agree. **It leaves when the question is answered, not at a fixed hour**. It showed until noon at first, but after 09:00 nothing new enters the night, and at 11:00 nobody asks about it any more. An hour after the low, because a late low — between 08:00 and 09:00 in 16 % of 1,476 nights since 2022, in winter in about a third, often a night still cooling at its end — is news at 09:00 too. Not earlier than 09:00: "an hour after the low, or until 09:00 if the low comes before 07:00" was considered and dropped, since a low at 06:59 would have shown until 09:00 and one at 07:01 until 08:01 (20 % of nights have their low between 07:00 and 08:00), and an end before 09:00 can flip back — the night is still running, and a colder point brings the line back with a new low. From 09:00 the low is fixed, so the line leaves once. Local time throughout, so DST nights are 14 and 16 hours (`public/night.js`). |
| Status hints | one at most, next to a tile's age in the warning colour, or whole on the line below when both do not fit — never split, never a third line; only when something is wrong, and the cause before the symptom: "kein Funkkontakt" while the station has lost an add-on module and no point has arrived since; "Batterie 18 %" at 20 % or less, whether or not values are late; "Funk schwach" / "WLAN schwach" at Netatmo's own "low" radio (`rf_status` ≥ 90) and "bad" Wi-Fi (`wifi_status` ≥ 86) levels, but only on a stale tile | The tile's age already says *that* values are late; a hint says *why*, or warns before anything is late. A weak signal shows only as the explanation of late values: a working module's radio ranges widely, so a single weak reading is noise. "Out of reach" needs no point newer than the status, because a reconnected module keeps delivering through `getmeasure` while a failing `getstationsdata` holds the status back. A flat battery is the usual reason a module drops out, so the battery outranks the lost contact. A hint split across two lines read as torn, hence the one-hint limit. The 20 % is a guess; revisit it with the first battery that actually runs low. |
| Server unreachable | a line in the bar at the foot of the page — *Keine Verbindung zum Server – letzte Antwort vor 2 Min.* — after two failed asks in a row; an ask fails when the values **or any series that was due** do not arrive, and when only a series is missing the line reads *Verbindung zum Server gestört – letzte Kurven vor 2 Min.* instead; the tiles keep the last values and age, and go stale by themselves | **"letzte Antwort", not "letzte Daten":** the time is the last contact with the server, not the age of the values. Once the wall read "letzte Daten vor 1 Min." next to tiles at "vor 2 Tagen", and it was taken as one-minute-old data: the server had answered, but with values two days old, because the poller had not caught up yet. **Two failures, not one:** a wall tablet whose WLAN drops single requests put the line up for one minute at a time while the server was fine; one ask later it was gone. A real outage is reported a minute later, which hardly matters next to tiles that say how old their values are. **The page never stops asking:** the hourly reload can hang when the server answers its HEAD and becomes unreachable before the page's own GET — a sleeping Mac waking in the dark for a few seconds does exactly that — so a reload under way still renders and arms the next ask, and the old page keeps the line honest until the new one arrives. **A failing tile cannot stop it either:** each tile renders on its own, so one that throws keeps what it last showed and its place, and the next ask is armed even when the render fails. Before, one exception ended the chain of asks and the hourly reload with it, and the wall showed one moment for good with ages that no longer moved, so nothing looked stale. **A missing series counts as a failure**: the curve, the low and high, the airing and window labels and the pressure arrow all come from the series. Once a wall on a link that lost most of its packets reloaded, got its values but none of its series, and showed only each tile's top line, with no curve, no labels and no line at the foot — so a room that needed airing looked fine. **It has its own wording**: with the values arriving, *Keine Verbindung zum Server – letzte Antwort vor 3 Std.* stood next to tiles at "vor 2 Min.", the same contradiction again. So *Keine Verbindung* is for an ask without any answer and keeps the last contact as its age, and *Verbindung zum Server gestört – letzte Kurven vor …* is for values without their series, with the age of the last full answer, which is how old the curves are; a page that never had a full answer reads *– keine Kurven*. The wording follows the last ask, so on a link that loses requests it can change from one minute to the next. **Only the series the page asks for by itself count:** the week behind a tap on a curve is fetched on request, and when it fails the tile keeps its day and the line stays as it is. **The hourly reload waits for a full answer too, and makes its ask fetch every series:** one answered HEAD let a page with curves replace itself with one that never got any. A series is otherwise fetched only for a new point, about every ten minutes, so most asks carry none and say nothing about whether the link can; the fresh page needs all of them at once. **A series that keeps failing therefore holds the reload back** for as long as it fails. That is accepted: the line is on the wall the whole time, and a page with old curves is worth more than a fresh one without. |

## Assumptions

- **High risk — the refresh token rotates.** Each renewal invalidates the
  previous token. If the stored token is lost or overwritten concurrently, the
  display stops and a *manual* recovery is due: generate a fresh pair in the
  portal and drop it into the token file. Exactly one writer; replace the token
  file atomically. Measured over two unattended days: 146 cycles, 15 rotations,
  none rejected.
  - The access token is valid for **180 minutes**.
  - **The refresh token does not expire with it.** Renewals that ran two hours
    late because the host was asleep were accepted, and so was one about 82
    hours after its access token had expired. A poller that was away for days
    recovers on its own; 82 hours is the longest gap tested, not a limit.
  - **A superseded refresh token was once still accepted 38 minutes after
    being replaced.** Do not build on it — one observation of a grace period
    whose length and existence are undocumented.
- **Medium risk — the API is not always there.** About 7 % of calls to
  `getstationsdata` fail with HTTP 503, never more than twice in a row.
  Retrying in the next cycle is enough and no backoff is needed. The display
  has to show how old the newest value is, because a tile that silently freezes
  for twenty minutes is a normal state here.
- **503s come in bursts, too.** During a first import, 3 of 4 `getmeasure`
  calls within nine seconds failed; 60 sequential calls a few minutes later all
  succeeded, so this was not throttling. A failure ends only that module's
  backfill for the cycle, and the next cycle resumes it. `getmeasure` has also
  failed for three cycles in a row, longer than `getstationsdata` ever did.
- **Medium risk — `getmeasure` returns past ranges completely**, so outages can
  be healed after the fact: the full history is there, at full resolution,
  back to the station's setup. A page is capped at 1024 points (about 3.5
  days), and `date_begin=0` starts at the first point. Two traps: an empty
  range comes back as `[]` rather than an object, and **an unknown `type`
  returns an empty page instead of an error**, so a misspelt type is
  indistinguishable from "no data". There is no absolute pressure in
  `getmeasure`. Gaps longer than ten minutes in a real history turned out to be
  Netatmo's own: it has no data in them either.
- **Low risk — rate limits** (50 requests per 10 s and 500 per hour per user,
  per Netatmo's documentation) are never in reach at a 10-minute cadence. The
  first import is the one exception — about 1,080 pages for four years of three
  modules. It is paced at 50 pages per cycle, one second apart, about 310
  requests an hour.
- **Low risk — an old tablet runs a current engine** for now. No CSS or
  JavaScript restrictions follow, but 3 GB of RAM on an old device still demand
  a lean, leak-free frontend. The insurance is an hourly self-reload.
- **Accepted — engine updates end with the next minimum-version raise.** Chrome
  has required Android 10 since Chrome 139 (August 2025). Once it raises the
  floor again, an Android 10 tablet keeps its last engine. The dashboard is
  plain HTTP on the LAN, so no certificate store is involved, and a page
  without framework or build step keeps working in a frozen engine for years.
  Do not reach for the newest web platform features.
- **Accepted — the tablet gets no more security patches.** It sits on the home
  LAN, opens one page from one server over plain HTTP and is used for nothing
  else; that is the whole exposure. The one account it needs is a Google
  account for Play Store updates, made for the tablet and with nothing behind
  it.
- **Accepted — the host need not run continuously** until the wall is up. Gaps
  in the series are closed by the backfill; only a permanent wall needs a host
  that is always on.

## The house

What the rooms and the outdoor module measure depends on the building they sit
in, and some rules have to allow for it.

- **Thick stone walls lag the outside by hours.** Stone conducts and stores
  heat well; walls half a metre thick lag the outside by about 12 hours and
  damp its swings, so room air is anchored to the walls, not only to the
  outside air. Hours of tilted windows with the outside a few degrees warmer
  moved a room by only about a degree, and it fell back toward its walls within
  an hour and a half, while the outside was still warmer. **Whatever judges the
  rooms against the outside has to allow for this:** after warm air has come
  in, a room cools on its own, toward its walls (*Window open*).
- **The outdoor module belongs in the shade.** One that sees direct sun for
  half an hour around noon shows a bump of a degree, which the plausibility
  filter keeps — it is real air, below the spike test's floor — and which is
  rarely the day's high. Mount it on a north-facing wall if there is a choice.

## Scope

In scope:

- One station: base unit, outdoor module, additional indoor modules
- Current values per module, history over hours and days
- Airing recommendation from absolute humidity and CO₂
- Indoor/outdoor difference, night low, pressure tendency
- Battery, radio and offline hints per module
- Forecast from Open-Meteo
- Night rendering: dimmed and reduced
- Kiosk operation: autostart, reload, survives a reboot
- Charge cycling for the wall tablet through a switched socket

Deliberately out of scope:

- The OAuth authorization code flow — each installation serves one account
- Access from outside the house — the Netatmo app covers that
- Other people's stations nearby
- User accounts, roles, multi-user operation
- Native app, app store, PWA offline mode
- Push notifications and alerts
- Cloud hosting of any kind

Later: rain and wind sensors with their own presentation (rain totals, wind
rose), and longer ranges than a week.
